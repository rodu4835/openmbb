OpenMBB — Info

What OpenMBB is

A read-first serial console + diagnostics tool for Gen2 MBB-based Zero motorcycles (2013–2019: S / SR / DS / DSR / FX / FXS / FXE). It talks to your bike's main board over an FTDI 3.3 V TTL cable to read health, settings and logs — and only writes after backing up and with your confirmation.

Do this PARKED. Key on (or the AC charger plugged in), kill switch off, never while riding.

The guided flow

  1. Test your cable — a listen-only check that proves the cable + baud are good and the bike is talking. Sends nothing, so it's safe on any wiring. No bike? Flip Simulator mode at the bottom of the first screen.
  2. Connect — wakes the console and confirms the firmware.
  3. Pull full database — one click reads everything (health, settings, errors, gearing) and saves a backup.
  4. Analyze — review the data with plain-language explanations of each value.
  5. Log in (optional, read-only) — reveals the tunable settings and unlocks the Writes tab.
  6. Writes — change a whitelisted setting; every write backs up all settings, reads the value back to verify, and journals it — a changed row shows a Reset button to restore the last read.

Commands & safety

Nothing is hard-blocked — see the Command reference tab for every command. Destructive ones are sendable from the raw command line, but require you to read the consequences and type confirm first. See the Safety tab for the full model.

Heavy log dumps (eventlogdump / dumpall) can briefly make the BMS open the drivetrain contactor — that's why they're gated and never run automatically. Each time the contactor opens, the bike also writes a permanent “Line Contactor o/c — VERY SEVERE” entry to its error log that OpenMBB cannot clear, so read the event log only when you need it. While a heavy read runs, OpenMBB shows a blocking “Reading — please wait” window that locks the rest of the app until the read finishes — then a Continue button appears (the console can only do one thing at a time, so don't send anything else mid-dump). eventlogdump is also where your ride history comes from — it prints the full event log as decoded text, so OpenMBB reads your rides straight off the bike (no Zero app or external tool). Pull it via Analyze → Rides → Pull ride log from bike, or tick also pull the full event log on the Read tab to fold it into a database pull.

Logs & diagnostics

dumpallcautionDump everything incl. logs (~1 MB, minutes) - same contactor caveat.
What it does
Dumps everything including the event logs (READ_TIPS: 'Everything incl. logs (~1 MB, minutes) - same contactor caveat.'). Because it includes the full event log it carries the same heavy/monopolize-the-console behavior as eventlogdump. Read-only content, never auto-run, GUI-gated behind a confirm dialog.
What could happen
Same as eventlogdump: while the console is monopolized for minutes the BMS can protectively OPEN the drivetrain contactor (audible click + flashing dash).
Reversible?
Yes - it reads data only; the contactor re-closes itself once the dump finishes. No persistent change.
How to recover
Let the dump finish; the bike re-closes the contactor automatically. Park the bike first.
eventlogdumpcautionDump the full event log (~1 MB, minutes) - can briefly open the contactor.
What it does
Reads the entire event log (~8600 entries / ~1 MB). At 38400 baud it streams for MINUTES and monopolizes the MBB long enough that it stops servicing the Sevcon/CAN bus. READ_TIPS: 'can briefly OPEN the drivetrain contactor. Park the bike first.' It is a read - it does not modify anything - and is never auto-run; the GUI gates it behind an explicit confirm dialog.
What could happen
The BMS protectively OPENS the drivetrain contactor while the console is monopolized (observed live: audible click + flashing dash). If the bike were moving, the drivetrain would drop out. It also ties up the console for minutes.
Reversible?
Yes - no data is changed; the contactor re-closes on its own once the read finishes. It is a read-only side effect, not a persistent state change.
How to recover
Wait for the dump to complete; the bike re-closes the contactor automatically and the dash returns to normal. Park the bike before running so a mid-ride contactor open is not a hazard.

Firmware & bootloader

resetcautionReboot / reset the MBB.
What it does
Resets the MBB (BLOCKED_COMMANDS). On the hard blocklist - never sent. Would reboot the controller and lose the logged-in console session/state.
What could happen
The MBB reboots mid-session: login level and console state are lost (transport treats a boot banner as a ConsoleRebootError). If sent while riding, a controller reset drops normal operation.
Reversible?
Partially - a reset is a reboot, not a data change, so the bike comes back up; but the current session and any in-progress operation are lost.
How to recover
Reconnect on the Connect tab and log in again. Never send while the bike is in motion.

ov_* (override family)catastrophicSafety-interlock OVERRIDES - any command starting with ov_.
What it does
BLOCKED_PREFIXES = ('ov_',): any token beginning with 'ov_' is a safety-interlock override and is never sent (also blocked as a 'set' name). _line_blocked: 'a safety-interlock override (ov_*) - never sent.'
What could happen
Disables or forces a safety interlock (the very guards - isolation, BMS, kill, etc. - that protect the pack and rider). Overriding an interlock can allow operation in an unsafe condition (e.g. isolation fault, BMS bypass).
Reversible?
No / unknown - an override defeats a protection; even if the override flag is cleared, any damage or unsafe operation it permitted is not undone, and the repo does not document safe re-enable.
How to recover
Not recoverable in the sense of undoing consequences; the only safe posture is to never send these. Restoring the interlock requires knowing the exact override state and is undocumented here.

Partially - the flag could in principle be set back, but the repo blocks it and does not sanction/verify the write, so a safe restore is not guaranteed; any crash consequence is irreversible.

Not supported by this tool; restoring ABS behavior would require re-enabling the interlock through sanctioned means. Do not attempt.

Safety model

USE AT YOUR OWN RISK. OpenMBB is an unofficial hobby tool, not affiliated with or endorsed by Zero Motorcycles or Sevcon/BorgWarner. Writing settings or sending console commands can damage your motorcycle, brick components, void your warranty, or create an unsafe riding condition, and may be irreversible. It has been verified only on a single 2017 Zero FXS (MBB rev 41) — behavior on any other model or firmware is untested, so the effect/recovery notes may not apply to your bike. No warranty; the authors accept no liability. See the LICENSE file.

Read-first, with a strong informed-consent gate for anything destructive. Nothing is hard-blocked — it's your bike — but a dangerous command typed into the raw command line makes you read what it does, what could happen, and how to recover, then type confirm before it's sent.

Input hygiene stays absolute: control characters and multi-line / pasted input are always refused (they could smuggle a second command).

Writes

The Writes tab is whitelist-only: speedo/gearing, custom-mode speed/torque/regen, and a few gauge/charge options — each with an effect + risk note and value limits. The guided path backs up all settings, sends the change, reads it back to verify, and journals it so you can revert. The regen/thermal guards are shown read-only. Coast regen of exactly 0 is refused (fishtail risk).

Always PARKED — key on (or AC charger), kill switch off, never while riding.

See the Command reference for the consequences + recovery of every command.
