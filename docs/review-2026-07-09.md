  fix: Make redaction session-scoped instead of call-scoped: keep a set of redact substrings on the Transport (added whenever exec_command is called with redact=...) and apply masking inside SessionLogger.raw / _drain for every write to disk, not just within the originating call.


# CRITIC GAPS
## G1 [MEDIUM] No stream-abort or resync after max_time expiry: a long command (e.g. `dumpall` from the raw box) leaves the MBB mid-stream and silently corrupts every subsequent command's captured response  (<repo>\src\openmbb\transport.py:157)
  claim: exec_command exits its read loop when `now - start > max_time` (transport.py:157) and returns the partial buffer, but nothing stops the bike, which keeps streaming. DUMP_COMMANDS (transport.py:22) omits `dumpall`, so sending it from the raw box goes through _read_cmd with idle_timeout=2.5/max_time=60 (gui.py:576-578) — at 38400 baud a ~1 MB dumpall takes 4-5 minutes, so the read cuts off after 60 s with 3-4 minutes of output still arriving. The next exec_command's pre-send drain is capped at 0.3 s (transport.py:133), so the leftover stream is captured as the NEXT command's response and saved to that command's per-command file with no error. Two silent corruptions compound: (1) the truncated file carries no truncation marker — it looks like a complete capture; (2) subsequent responses are misattributed for minutes. The real capture explicitly lists `dumpall` as the owner's planned archival command ('Optional later: dumpall to a file'), and the sim answers dumpall instantly (sim.py:328), so this failure mode has never been rehearsed. The same desync happens if any DIY-cable hiccup makes real dumplogs outrun max_time=900.
  fix: Three small changes: (1) add `dumpall` to DUMP_COMMANDS so it gets dump-class timeouts; (2) when exec_command exits via max_time (or via idle timeout without seeing PROMPT_RE), append a visible '### TRUNCATED: max_time/no-prompt ###' marker to the saved file and set a flag on Transport; (3) before returning (or before the next send), drain until the line is quiet-for-N-seconds AND the prompt is seen, so the wire is resynchronized to a known prompt state before any further command is attributed.

## G2 [MEDIUM] The field-proven Stage-1 listen-only cable check cannot be performed in the GUI — Connect & Probe transmits within seconds, and the 3-s listen is useless because the checklist says to key ON before connecting  (<repo>\src\openmbb\gui.py:495)
  claim: The captured session's safe bring-up procedure (mbb-console-session-2026-06-21.md §1, §4) is explicit: Stage 1 = listen-only with the FTDI TX (Orange) disconnected while powering the bike, so the boot banner proves RX wiring/baud with the PC physically unable to transmit; 'repeat it on the other PC' — i.e., on THIS machine for the first OpenMBB session. The GUI has no listen-only mode: _connect's job listens for only 3 s (gui.py:495) and then immediately transmits a CRLF. Worse, the on-screen checklist (gui.py:456-461) instructs 'key ON' BEFORE connecting, so by the time the user clicks Connect & Probe the boot banner is long gone and the 3-s listen predictably yields 0 bytes — it provides zero wiring diagnostics, and the very first thing the app does on an unverified DIY cable is transmit. If Tx/Rx are miswired, the first evidence arrives only after the app has already been driving the bike's Tx line.
  fix: Add a 'Listen only (Stage 1)' button on the Connect tab that opens the port, calls tr.listen(45) with on-screen instructions ('now power the bike / plug in the charger'), then reports byte count and whether boot-banner signatures ('Zero Motorcycles MBB', 'Checking EEPROM', 'Reset Source:') were seen — matching the field procedure exactly, with the option to run it Orange-disconnected. Also fix the checklist to say the banner test is done by powering the bike DURING the listen window, not before.

## G3 [MEDIUM] Probe success never requires the `version` read to parse — an empty or garbled version banner still yields CONNECTED, and there is no rev-41/FXS identity gate on any downstream behavior  (<repo>\src\openmbb\gui.py:512)
  claim: After the prompt check, _connect runs `ver = tr.exec_command("version", idle_timeout=1.5)` (gui.py:512). If the bike gives no reply within ~5 s, exec_command returns an empty string without error; done() then sets connected=True, the Firmware Rev regex (gui.py:524-525) silently fails, lbl_ver is blank, and Phase 1 unlocks anyway. So the probe's success criterion is only 'saw something prompt-like' (already flagged as too loose) — the one read that could positively authenticate 'this is a Gen2 MBB console at the right baud' is captured but never enforced. Separately, the entire safety model is firmware-specific: the blocklist was verified against the rev-41 menu, the write whitelist/validators against rev-41 semantics, and the About text says 'Verified on the 2017 FXS (MBB rev 41)' — yet nothing warns if the connected bike reports a different rev (future firmware update, BMS console, a friend's Gen2). A pre-flight identity check is cheap and the version banner format is confirmed ground truth (capture Appendix A: 'Firmware PN : 75-08036  Firmware Rev : 41').
  fix: Treat a version banner that does not match the known shape (Board PN 40-xxxxx / 'Firmware Rev : <n>') as a probe FAILURE with the same stop-and-recheck message as no-prompt. When it does parse, compare rev against a KNOWN_FIRMWARE_REVS = {41} set and show a prominent yellow warning ('firmware rev %s — safety lists were verified against rev 41 only') if it differs, before unlocking Phase 1.

## G4 [MEDIUM] FULL BASELINE is all-or-nothing: one serial hiccup during the final ~5-minute dumplogs discards the whole pass, and settings_baseline_*.txt is only written after every dump completes  (<repo>\src\openmbb\gui.py:608)
  claim: _baseline's job runs all 15 commands in one try-less loop (gui.py:608-619) and saves the labeled settings baseline only after the loop finishes (gui.py:620-622) — i.e., after eventlogdump, errorlogdump, AND the ~1 MB dumplogs. Any exception (a DIY-cable USB blip, FTDI enumeration glitch, the charger-powered MBB nodding off) at minute 8 of the sequence propagates out: results are discarded, no settings_baseline file is written even though `set` succeeded minutes earlier, baseline_done stays False, and the only recovery is re-running the entire sequence including the long dumps. On the first real session — the exact scenario where an unproven cable is most likely to hiccup — this turns one marginal connection into repeated 10-minute attempts, and the safety-relevant artifact (the settings backup) is held hostage by the least reliable, least safety-relevant step (dumplogs). Per-command .txt files do persist via the transport, but nothing tells the user their `set` capture from the failed pass is intact and usable.
  fix: Save settings_baseline_<stamp>.txt immediately after the `set` command returns (before starting the dumps). Wrap each command in try/except, record per-command ok/failed status, and finish the baseline with a summary instead of aborting; gate baseline_done on the essential reads succeeding (version, status, stats, and a non-empty parseable `set`) — which also dovetails with the already-confirmed 'baseline unlocks on empty captures' fix — while letting a failed dumplogs be retried alone.

## G5 [MEDIUM] The first baseline will almost certainly be captured on-charger, but the session records no power-state context and the checklist actively steers away from the proven charger-powered procedure  (<repo>\src\openmbb\gui.py:456)
  claim: The real capture's biggest data-quality lessons (mbb-console-session-2026-06-21.md §2, §3.4, §4) are: (a) plugging in the AC charger is how you power the console — no key-on needed — and (b) any reading taken on-charger has known artifacts: isolation resistance reads falsely low (32 kOhm vs healthy megohms, a documented Zero false-positive), SOC is pinned at/near 100%, and status shows 'Mode: Charging'. The GUI's connect checklist (gui.py:456-461) and WIRING_TEXT (gui.py:88-101) say only 'key ON' — never mentioning the charger option or its caveats — and nothing in the session pipeline extracts or stamps the power state: the `status` capture contains the Mode line, but no metadata file, no baseline filename tag, and no Health-panel annotation records that this baseline is an on-charger snapshot. That first baseline becomes the permanent reference every future Compare diffs against; months later there will be no way to tell (short of re-reading raw captures) that its SOC/voltage/isolation context was charger-contaminated. This is adjacent to but distinct from the confirmed 'health ignores isolation' finding — that is about the analyzer missing the warning; this is about the tool never recording the condition that makes the warning (and other baseline numbers) suspect.
  fix: During baseline done(), parse the Mode line from the `status` capture and write a small session_meta.txt (power mode, timestamp, firmware rev); if Mode is Charging, show a one-line note ('baseline captured while charging — isolation reading and SOC context are not valid off-charger') and have the Health panel display the same tag. Update the checklist to describe both power options (key ON vs AC charger) with the isolation caveat, since the charger is the procedure the owner actually uses.

# CRITIC SUMMARY
The six-dimension review covered the safety-gate bypasses, parser/firmware mismatches, and phase-state bugs thoroughly, but it under-covered the procedural shape of the first session itself. Reading the tool against the real 2026-06-21 capture's proven bring-up procedure exposes five gaps: (1) there is no stream-abort/resync when a command outruns max_time — and `dumpall` (explicitly planned in the owner's next-steps notes) is missing from DUMP_COMMANDS, so a raw-box dumpall is silently truncated at 60 s with no marker and then desynchronizes and misattributes every command response for the next several minutes; (2) the field-proven Stage-1 listen-only cable check (power the bike during a long listen window, TX disconnected) cannot be performed in the GUI — Connect & Probe transmits within seconds and its 3-s listen is provably useless because the checklist says to key ON first; (3) probe success never requires the `version` banner to parse, so an empty/garbled version still yields CONNECTED, and there is no rev-41/FXS identity gate even though every safety list was verified against rev 41 only; (4) FULL BASELINE is all-or-nothing with the settings backup written last, so a single DIY-cable hiccup during the closing ~5-minute dumplogs discards the pass and the safety-relevant artifact; and (5) the first baseline will be captured on-charger (the owner's actual power procedure) yet no power-state metadata is ever recorded, permanently contaminating the reference session that all future comparisons diff against. None can write to the bike, but (1) and (3) can silently corrupt what the user believes the bike said, and (2), (4), (5) determine whether the first session is diagnostic, wasted, or misleading.
